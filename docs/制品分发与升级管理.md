# 制品分发与升级管理

## 1. 统一管理对象

一次公共平台发行同时包含六类版本：公共源码、应用镜像、核心 Chart、上游 Chart 与镜像闭包、数据库迁移、中文资源与身份主题。它们各自有版本，但必须在同一发行清单中关联。

| 对象 | 推荐身份 | 保存位置 |
|---|---|---|
| 源码 | Git commit、构建输入清单 | GitHub 仓库与发行记录 |
| 应用镜像 | OCI manifest digest | Harbor 私有项目 |
| Helm 包 | Chart SemVer、包 SHA256、OCI digest | 同一 Harbor 项目的 OCI Chart |
| 上游依赖 | 上游发行、源 digest、目标 digest、架构 | 上游锁与离线包 |
| 数据迁移 | 递增迁移号和原 SQL 摘要 | 源码与备份清单 |
| 工具与主题 | 工具版本、校验值、模板来源和修改说明 | 发行工具闭包与中文资源 |

Harbor 的 OCI 仓库可以统一保存镜像和 Helm Chart，GitHub 保存小型源码、清单、流水线和发布说明。大镜像、数据库备份、凭据和原始现场证据不进入 Git 历史。

## 2. 入口与现场参数分离

公开仓库只描述 registry、namespace、Secret 引用和存储档位等参数。出口主机、代理、反向 SSH 隧道和内网地址记录在受控现场文档中。安装者不能从一个模板中的示例地址推断真实路由。

受控出口必须显式使用配置的代理下载。访问内部制品仓库应显式绕过公网代理，沿用已核实的内部或回环隧道入口。下载、上传和安装分段记录摘要、请求 ID 与结果；等待超时后先查询原请求，不能重复创建发布动作。

## 3. 上游进入 Harbor 的流程

1. 从当前维护入口获取 Chart，锁定明确版本；先检查 deprecated、维护仓迁移和破坏性变化。
2. 对照索引公布的 SHA256 验证包，保留 URL、版本、上游 commit/tag 与来源时间。
3. 使用真实 profile 渲染模板，提取实际启用容器、initContainer、hook 和测试镜像。关闭的可选组件不当作已启用能力。
4. 下载指定架构镜像和必要工具、插件、前端资源、身份主题、迁移与规则；校验完整闭包。
5. 推送到独立 Harbor 项目，回读目标 digest。源 manifest、归档、目标 manifest 是不同身份，格式转换后分别登记。
6. 以目标 digest 生成现场锁；`harbor-post-renderer.py` 拒绝未登记镜像，避免 Chart 升级偷偷引入公网镜像。
7. 推送上游原 Chart 到 OCI 仓库，保留所有权。自研 Chart 不冒充上游版本，也不修改第三方源码来满足本平台页面需求。

镜像标签便于检索，运行提升以摘要为准。更新标签不能替代重新取得相应制品资格。

`deploy/public-artifacts.lock.json` 固定已使用的自产 Chart 和命名渲染器。存量 Collector 的 `OPS_COLLECTOR_WORKLOAD_NAMES` 必须按当前 release 单独配置。升级前验证绑定的 Service、控制器 selector 与实际采集身份。Helm 4 在接管预创建对象时需要一致的服务端字段管理者，出现冲突先核对实际所有者及旧修订，按发行回退。

## 4. Chart 分层和资源归属

- `ops-platform`：API、Worker、参考服务、平台数据库与最小命名空间读取角色。
- 遥测后端 release：Prometheus/Alertmanager/exporter、Loki、Tempo、Collector、Grafana，分别锁定来源和生命周期。
- 身份 release：独立 Dex 与受控配置；角色映射和平台授权仍由 Core 执行。
- 现场 overlay：证书、Secret、registry、存储类、访问地址和资源预算；不提交公开仓。

只有 release 的 owner 可以升级或退役其资源。现有 CRD、CNI、存储 provisioner、其他业务 release 以及外部身份源不归平台自动接管。

从授权终端运行 `python3 tools/component-inventory.py --format markdown` 查看现场组件与修订。JSON 版本保留每个容器的声明摘要、运行 imageID、PVC 与保留策略，可用 `--baseline` 比较已审查的同环境清单。Prometheus 自身、Alertmanager、node exporter 和 kube-state-metrics 属于同一 Helm 发行，各自容器和存储仍单独核对。详见[端到端方案](公共观测平台端到端方案.md)。

## 5. 版本更新的门

普通补丁与大版本变化采用同一基本链路：来源核实 → 候选锁 → 配置渲染 → 合同与语义验证 → 隔离运行 → 恢复与升级验证 → 中文回归 → 制品提升。

大版本额外检查数据库格式、对象存储布局、Collector 插件、查询语义、端口、标签和资源 selector。Tempo 的单体与分布式模式、是否需要 Kafka，必须按选定版本和模式核实，不能由版本号猜测。Grafana Chart 维护仓迁移与 Grafana 应用数据库迁移分别评估。

首次建设已经发现旧 Grafana/Tempo Chart 弃用。迁移到受维护的社区 Chart 并选择经过验证的应用版本，属于实际升级任务，不能删除 deprecated 字段后宣称恢复支持。

## 6. 回退的两个边界

Helm rollback 主要恢复 Kubernetes 声明，不自动恢复 PostgreSQL schema、Grafana 数据库或 Tempo/Loki 数据格式。升级前必须知道哪些变化可逆、哪些只能从备份恢复。

应用使用 expand-contract 迁移。已经发布的迁移文件不改写；新增 SQL 用递增号登记。旧版读取窗口与新 schema 的兼容要通过测试，不能在回退时删表以获得启动成功。

有状态后端升级先保存对应一致性备份。实际演练应证明旧数据仍能读取、失败时能恢复到明确版本，并报告恢复耗时和数据缺口。恢复出的环境必须重新核对权限、密钥引用与来源覆盖。

本平台的本地 Loki 存储必须显式设置 StatefulSet 的缩容与删除保留策略为 `Retain`。停写前核验已绑定 PVC 的 UID，停写后复核 UID 一致再读取。升级后检查运行策略与渲染结果一致。

## 7. 许可证、SBOM 与可追溯来源

选定镜像、Chart、插件与依赖应逐项登记 SPDX、LICENSE/NOTICE、修改情况和 SBOM。保留上游源码获取地址及版本，必要的离线来源随发行闭包保存。不能因为项目主页开源就推断所有企业插件、二进制发行或衍生资源适用相同许可。

当前公共工程不包含自研的第三方内核补丁。身份主题属于受支持的外部配置与模板覆盖，应记录其上游来源和中文修改，不修改发布二进制。
