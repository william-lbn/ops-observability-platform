# 组件命名与部署精简

当前公共平台使用独立命名空间、标准开源后端和中文工作台。精简的优先顺序是收好验收资源、消除重复采集、按实测决定是否合并常驻实例。命名由上游项目与用途决定，覆盖 Pod 的控制器名称、组件清单和运维手册。

## 1. 把运行成本和列表噪音分开

当前六节点验证环境盘点如下。数字是现场快照。

| 类别 | 运行 Pod | 职责 |
| --- | ---: | --- |
| 公共平台 | 4 | 两个接口服务，一个后台采集服务，一个平台 PostgreSQL |
| 指标和规则 | 9 | Prometheus、Alertmanager、kube-state-metrics 各一，node exporter 六个 |
| 日志、Trace、专家页与身份 | 4 | Loki、Tempo、Grafana、Dex 各一 |
| 采集入口与白名单日志 | 9 | 平台及测试租户 A/B 的三个 Collector 网关，六个节点日志 Collector |
| 主命名空间验收 | 2 | 参考服务和验收客户端 |
| 另外两个租户命名空间 | 2 | 两个同名参考服务 |
| 隔离恢复 | 5 | PostgreSQL、Dex、接口服务、后台采集服务、Grafana 副本 |

主命名空间共 28 个运行 Pod。四个命名空间合计 35 个运行 Pod，另有 12 个已结束 Pod。六个 exporter 和六个日志采集器对应六节点，缩成一个副本会丢掉节点覆盖。kube-state-metrics 已为节点 Ready 和副本失败告警提供数据，目录轮询也另有对象身份和新鲜度职责。

建议在结束验收后回收有证据可查的恢复与参考工作负载，并把完成的 Job 和临时客户端纳入统一到期回收。常态目标为 **24 个运行 Pod**，按现有职责计算含两个每节点 DaemonSet，保留一个平台 Collector 网关。两个试验租户及相关网关进入按需验收档。存量事件、日志和恢复证据照常保留。真实租户入驻时，入口副本与容量依据各租户需要重新计算。

## 2. 按使用目的选择简洁的部署方式

| 选择 | 当前判断 | 改变条件 |
| --- | --- | --- |
| Loki 和 Tempo 单体 | 适合当前验证量和单卷档。保持各自后端与生命周期 | 实测查询与写入资源竞争，或明确提出独立伸缩、跨故障域存储和保留时间要求时再评估分布式 |
| 一个平台 Collector 网关和每节点日志 Agent | 平台 OTLP 身份与 HostPath 文件权限分离。节点本地日志需要每节点采集 | 上游已有合格 Agent 能交付同样白名单日志时，验证单一采集责任，再切换 |
| 每租户专用 Collector 与共享网关 | 已验证专用入口的来源 mTLS、认证和固定分区。共享网关是规模增大后的候选 | 必须同时验证受信任租户路由、跨来源证书负向、独立资源预算、噪声邻居以及一条流水线故障时其他租户仍可用 |
| node exporter 与 Collector hostmetrics 合并 | 暂缓。节点资源、磁盘、丢包图依赖现有指标、单位和标签合同 | 同一节点用短时间重叠对照，映射全部依赖指标和规则，核验特权、CPU 与内存开销，再单路切换 |
| eBPF 与 Hubble | 用于网络故障专项，而非默认常驻依赖 | 明确需要服务流与连接拒绝证据，再在隔离环境验证作用域、开销、采样及退出。新增工具须有不可被现有信号替代的诊断价值 |
| 增加长保留、独立查询或高可用后端 | 维持当前本地卷验证档 | SLO、实例规模与故障域先确定。比较复用已管理的后端和独立扩容两种路径，按实测成本与恢复承诺选择 |

节点 Agent 负责主机本地数据，网关负责集中接入、处理和转发。业务 SDK 的 OTLP、Prometheus 的主机指标、应用 Trace 与节点网络流有不同观测范围。设计每条信号的唯一常态采集路径，减少重复上报及重复告警。[OpenTelemetry Agent](https://opentelemetry.io/docs/collector/deploy/agent/) · [OpenTelemetry Gateway](https://opentelemetry.io/docs/collector/deploy/gateway/) · [Loki 部署模式](https://grafana.com/docs/loki/latest/get-started/deployment-modes/) · [Tempo 部署模式](https://grafana.com/docs/tempo/latest/reference-tempo-architecture/deployment-modes/)

## 3. 命名合同

开源组件的工作负载名应保留上游项目名。用途和实例后缀说明平台、网关、节点或租户。自研组件用 `ops-observability-<职责>`。采集来源的稳定标识和技术对象名分别管理，改 Pod 名无需改历史事件或租户分区。

| 类型 | 目前名称 | 目标工作负载名称 |
| --- | --- | --- |
| OpenTelemetry Collector，平台入口 | `ops-collector` | `opentelemetry-collector-platform-gateway` |
| OpenTelemetry Collector，验收租户入口 | `ops-collector-a/b` | `opentelemetry-collector-test-tenant-a/b` |
| OpenTelemetry Collector，节点日志 | `ops-infra-logs-agent` | `opentelemetry-collector-node-logs`，保留 Chart 生成的角色后缀 |
| 自研观测平台接口 | `ops-api` | `ops-observability-api` |
| 自研观测平台后台采集 | `ops-worker` | `ops-observability-worker` |
| 自研验收参考服务 | `ops-reference` | `ops-observability-test-reference` |
| 其余开源组件 | `ops-prometheus`、`ops-alertmanager`、`ops-node-exporter`、`ops-kube-state-metrics`、`ops-loki`、`ops-tempo`、`ops-grafana`、`ops-dex`、`ops-postgres` | 保留；名称已含项目或官方镜像名 |

标准标签中 `app.kubernetes.io/name` 表示项目，`instance` 绑定 Helm 发行，`component` 表示职责，`part-of` 表示归属。命名验证读控制器实际模板与 Pod 所属关系。控制器名和 Helm release、Service DNS、证书 SAN、PVC 都可能独立变更，按各自依赖审核。[Kubernetes 推荐标签](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/) · [StatefulSet 与卷身份](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)

## 4. 落地与验收顺序

1. **现场基线**。保存实际控制器、镜像、来源和租户、抓取目标、运行/结束 Pod 数，以及告警和认证依赖。恢复演练留存检查记录和密文后回收临时实例。
2. **名称候选**。在隔离档渲染 Chart，先检查每个名字、Pod selector、Service、NetworkPolicy、ServiceAccount 与 RBAC、指标发现和证书校验。存量 Collector 通过已有 Helm 渲染器保留老 Service DNS，继续使用原证书身份。所有 PostgreSQL、Loki、Tempo、Prometheus、Grafana 等数据卷绑定保持原权威路径。
3. **分开切换**。先从自研无状态组件开始，保留既有入口 DNS、端口和角色。准备新副本，验证真实请求和后端，切换发现与路由，回读旧版可访问的历史，再回收旧副本。Collector 切换另外核对来源 TLS 名称、固定分区、接收/出口和失败回退。文件采集一节点一条读取链，切换前对照读取位置和重放风险。
4. **精简验收档**。验收资源按窗口运行。退出窗口时撤除对应临时实例，来源明确显示停用或未观测。保留双租户自动测试入口和定期重复执行能力。无状态改名、数据迁移和副本合并分别通过，便于归因。
5. **端到端门**。验证平台指标、白名单日志、两租户日志与 Trace、告警及历史看板继续可读。用真实后端将停写、空结果和未取得样本区分开。报告 Pod 数、每节点覆盖、资源基线、查询与恢复结果，才能接受精简。

当前 Grafana 中发现两个历史数据源使用旧连接配置，实际返回 400。迁移需先检查仪表板和告警是否引用旧 UID，再将引用迁到固定身份的新数据源，验证日志到 Trace，再退役失效数据源。
